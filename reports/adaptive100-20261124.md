# Per-player 100kbps cadence feedback — 2026-11-24

Implemented and deployed an opt-in C-profile controller using
`adaptiveBandwidth: true` and `mlogent-world-bandwidth.service`.

The passive collector observes public eth0 IPv4 game-port 6567 outbound IP
bytes (TCP and UDP headers included), aggregates ephemeral peer totals every
two seconds, and feeds the existing local world API. No packet payloads or
addresses are persisted. Addresses shared by multiple players are divided
equally; this is an estimate, not exact per-connection attribution. Discovery
and map transfers on that address also contribute. Noninitial fragments are
unclassifiable and omitted; raw-socket capture can drop traffic under load.

Each receiver has an independent EMA (0.2 new / 0.8 old), 100000bps target,
110000bps downshift threshold and 85000bps recovery threshold. Three high
feedback windows plus a ten-second change cooldown allow one downshift;
eight low windows plus a twenty-second cooldown allow one recovery step.
Initial adaptation waits twenty seconds. Normal-camera intervals are
200/250/300/400ms; full-view intervals are 300/350/400/500ms. Six far buckets
therefore cover a round in approximately 1.2–2.4s at those target cadences.
Phase deadlines advance without accumulating per-dispatch scheduling drift or
burst catchup; actual timing still depends on the game thread and available
staggered dispatch opportunities.

This is feedback cadence control, not a hard byte shaper or a token-bucket
implementation. It does not predict/serialize each entity ahead of sending.
Controlled mobile units retain 100ms supplementation, reactors 500ms, and
building/event/state traffic remains on existing paths. Their irreducible
cost may exceed the target. The controller never drops critical packets to
force compliance. PvP uses its existing path. Missing feedback beyond ten
seconds restores ordinary C cadence. Map load clears receiver controller state;
disconnect feedback cleans inactive entries. The collector never wakes a world.

## Validation

`python tools/check.py`: 39 tests passed, covering independent receivers,
EMA/cooldowns, bounded levels, shared-address apportionment, stale-monitoring
fallback, map/disconnect cleanup, per-player dispatch and public-port packet
classification. Existing fog, priority, dedup, preview and safety tests passed.

Final live version was hot-installed on Broken Moon Islands with one player
and approximately 97–99 units. The measured rate initially reached about
173kbps; after the startup grace it increased the normal unit interval from
200ms to 300ms and then 400ms while the smoothed signal decayed. A later
69kbps window / 77kbps EMA triggered gradual recovery to 300ms. Latest sample
was 90.28kbps measured / 90.66kbps EMA at 300ms, interest enabled and no fallback.
This demonstrates actual downshift and recovery, not a controlled gameplay
quality or capacity benchmark. The first threshold crossing overshot; target
tracking is intentionally coarse and may vary with camera/game activity.

One manual API probe timed out, while passive telemetry and controller feedback
continued. Subsequent status was available and showed no synchronization
fallback. Final live policy work peak was 30.75ms in this sample; earlier
installation warmup had a separate 178.73ms peak. Causes are not attributed.
Collector resident cgroup memory was about 12.8MB and restart count zero.

Source and profile are persistent; service enabled at boot. Backup directory:
`out/deploy-backups/adaptive100-20261124` on the operations deployment.
Live rollback sets `this._mcpSnapshotPolicy.adaptiveEnabled=false`; set profile
`adaptiveBandwidth` false to persist rollback. The other C optimizations remain.
